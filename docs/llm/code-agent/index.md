## 在解决什么问题

单轮代码生成已经比较成熟：给个函数签名和注释，模型补全。但真实的软件工程任务是**另一个物种**：

- 需求是一句 issue，可能连在哪改都不知道
- 仓库有几万行，跨几十个文件
- 改完要跑测试，失败要看日志、再改
- 一次任务可能要几十步，中间任何一步走错都前功尽弃

Code Agent 方向研究的就是：**怎么让模型在真实仓库里，通过读代码、改代码、跑测试，完成长程任务。**

## Agent 的基本循环

```text
观察（issue + 仓库结构 + 上一步结果）
  ↓
决策（读哪个文件 / 搜什么 / 改哪里 / 跑什么测试）
  ↓
执行（shell、编辑器、测试框架）
  ↓
观察（编译错误、测试输出、diff）
  ↓
循环，直到测试通过或步数耗尽
```

一个最小实现大概长这样：

```python
def run_agent(issue, repo, max_steps=50):
    obs = repo.overview(issue)
    for _ in range(max_steps):
        action = policy.act(obs)          # read / search / edit / run_tests
        result = repo.execute(action)
        obs = obs + result
        if result.tests_passed:
            return "resolved"
    return "unresolved"
```

难点几乎都在这三步里：**决策要基于长上下文、动作空间是开放的、奖励要等几十步之后才知道**。

## 能力栈

| 层次 | 内容 | 关键问题 |
| --- | --- | --- |
| **Code 预训练** | 代码语料、FIM（fill-in-the-middle） | 语料质量、许可证、去重 |
| **指令微调** | 代码指令、工具调用格式 | 格式统一、拒绝无意义调用 |
| **仓库理解** | 长上下文、检索、调用链、代码图 | 几万行怎么塞进上下文 |
| **Tool Use** | shell、文件读写、grep、测试、linter | 动作空间设计与错误处理 |
| **执行反馈** | 编译错误、测试失败、栈回溯 | 怎么把噪声变成有用信号 |
| **代码 RL / Agent 训练** | 用测试结果做奖励，训练多步策略 | 稀疏奖励、长程 credit assignment |
| **数据构建** | issue-PR 对、合成 bug、测试生成、轨迹 | 数据规模与真实性 |

## 训练方法

### 1. SFT on trajectories

收集成功轨迹（人类或强模型），把「观察 → 动作」序列当训练数据。关键是**轨迹格式统一**：工具调用怎么表示、错误输出怎么截断、多轮怎么拼接。

### 2. 拒绝采样 + 专家迭代

同一个 issue 采样多条轨迹，只保留测试通过的，再拿去微调。简单有效，但受限于模型的探索能力——解不出来的题永远采不到正样本。

### 3. RL with execution reward

奖励来自测试：全过给 1，否则 0（或按通过比例给部分分）。

- 奖励**稀疏**：几十步只有最后一步有信号
- 轨迹**长**：一条轨迹可能上万 token
- 环境**慢**：跑测试要几秒到几分钟

常见缓解：过程奖励（每步是否有进展）、课程学习（从单文件 bug 到跨文件）、把任务拆短。

### 4. 过程监督

给中间步骤打标签：这个文件读对了吗、这个修改方向对吗、这个测试该跑吗。PRM 在代码任务上比结果奖励更容易训，但标注成本高。

## 数据怎么来

| 来源 | 说明 |
| --- | --- |
| **issue–PR 对** | 真实仓库的 issue 和修复 PR，SWE-bench 就是这么构造的 |
| **commit 历史** | 一次 commit 就是一个「问题 + 修复」样本 |
| **合成 bug** | 在正确代码上注入 bug，测试就是验证器 |
| **测试生成** | 模型先写测试再写实现，测试本身成为奖励 |
| **轨迹采集** | 让强模型/人类在容器里做题，记录完整交互 |

!!! warning "数据泄漏"

    仓库的测试文件、issue 讨论里经常直接包含答案。构造数据时要把「修复后的代码」和「测试断言」从上下文里剔掉，否则模型学的是抄答案。

## 评测

| Benchmark | 考什么 |
| --- | --- |
| HumanEval / MBPP | 单函数生成，pass@1 |
| LiveCodeBench | 新题、防污染，覆盖竞赛题 |
| RepoBench | 仓库级补全与检索 |
| SWE-bench | 真实 GitHub issue，跑测试判定 |
| SWE-bench Verified | 人工筛过的子集，减少歧义题 |

除了 resolve rate，还要看**成本**：多少步、多少 token、多少美元。一个 60% 但贵十倍的方案，工程上未必可取。

## 学习路径

1. **代码模型基础**：代码预训练、FIM、指令微调；先能训一个小的代码模型
2. **Agent 基础**：工具调用格式、ReAct 循环、上下文管理
3. **仓库理解**：长上下文、检索、代码图；从「单文件」到「跨文件」
4. **执行反馈**：怎么解析编译错误/测试输出，怎么决定下一步
5. **训练**：SFT on trajectories → 拒绝采样 → RL with tests
6. **评测**：搭一个能跑 SWE-bench 子集的评测环境

## 面试常问

**Q：Code Agent 和普通的代码补全有什么区别？**

补全是单轮、局部、无环境交互；Agent 是多轮、仓库级、有执行反馈，动作空间包含读文件、搜索、改代码、跑测试。

**Q：仓库太大放不进上下文怎么办？**

检索（BM25/向量）、结构信息（目录树、import 图、调用链）、分层摘要、长上下文模型；实践中常常是「检索 + 让模型主动 grep」。

**Q：奖励怎么设计？**

最直接用测试结果（全过/部分过）；稀疏时加过程奖励或中间信号（能否编译、是否改对文件）；要防止模型改测试来「通过」。

**Q：怎么防止模型作弊？**

测试文件只读、diff 只允许改源码目录、跑测试用干净环境、检查是否修改了断言。

**Q：长程任务的 credit assignment 怎么做？**

把轨迹切段、用 step-level 价值估计、或者用「是否更接近通过」做中间奖励；也有工作直接用结果奖励 + 更长的训练。

**Q：SWE-bench 的分数怎么解读？**

看 Verified 子集、看 resolve rate、看成本；注意模型是否见过仓库（污染），以及测试是否 flaky。

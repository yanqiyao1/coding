<!-- more -->

## 为什么写

学东西的时候有个很常见的错觉：看懂了、跑通了，就等于会了。但真到要给别人讲清楚「为什么这里必须写成 `size_t`」「为什么这个循环反过来写慢了六倍」的时候，才发现中间还隔着一层。

写下来的过程就是补这层的过程。所以这里的东西首先是写给我自己的——把踩过的坑、查过的文档、量过的数字整理成可以复用的结论；顺手发出来，如果对别人有用就更好了。

## 写什么

只写代码层面能讲清楚的东西：

- C / C++：对象模型、未定义行为、编译器优化
- 系统：进程、内存、链接、调试、性能
- 工具：编译器、CMake、Git、Shell
- 算法：重点是「为什么这样写更慢」，不是题解

不写框架速成，不写没有跑过的性能数字，不写「十招精通」。

## 怎么组织

文章分两层：

1. **博客**（[这里](../index.md)）按时间倒序，适合随手翻；
2. **系列**（[那边](../../series/index.md)）按线索组织，适合从头读。

同一篇文章会同时出现在两边。系列页里有阅读顺序和「接下来写什么」的计划，比时间线更能反映知识的结构。

## 这个站是怎么搭的

需求很简单：中文写作排版要好看、代码要高亮、不能挤占我的个人主页（那是个独立的学术主页，放在 `yanqiyao1.github.io`）。

选型是 [MkDocs Material](https://squidfunk.github.io/mkdocs-material/)：

- 纯 Markdown 写作，配置就是一个 `mkdocs.yml`，没有前端构建
- 代码高亮、admonition、tabs、脚注、Mermaid 都是现成的
- 构建产物是纯静态文件，扔给 GitHub Pages 就行
- 主题本身对中文支持不错（搜索需要 `jieba` 分词）

部署用的是 GitHub Actions 的 Pages 流程，整个链路是这样：

```mermaid
flowchart LR
  A[本地写 Markdown] --> B[git push 到 main]
  B --> C[GitHub Actions 构建]
  C --> D[mkdocs build --strict]
  D --> E[上传 site/ 产物]
  E --> F[GitHub Pages 发布]
```

因为是独立的仓库 `yanqiyao1/coding`，站点地址是 `https://yanqiyao1.github.io/coding/`，和主页 `https://yanqiyao1.github.io/` 完全分开。主页那边一行都不用改。

## 写作流程

新文章靠一个小脚本生成骨架：它会带上日期前缀、front matter 和「摘要分隔符」，文件名决定 URL。

=== "新建文章"

    ```bash
    make new TITLE="gdb 的第一小时" SLUG=gdb-first-hour CATEGORY="系统与调试"
    ```

=== "本地预览"

    ```bash
    make serve          # http://127.0.0.1:8000/coding/
    ```

=== "发布"

    ```bash
    git add -A && git commit -m "post: gdb 的第一小时" && git push
    ```

推上去之后大概一分钟，Actions 会跑完构建并发布。构建是 `--strict` 的：链接写错、图片路径错、页面没进导航，都会直接失败，不会悄悄发上线。

## 几个约定

!!! note "关于代码"

    文章里的代码都在 `-Wall -Wextra` 下编译过；性能数字都注明了机器、编译选项和数据规模。数字的意义在于数量级和趋势，不在于小数点后两位。

    发现错误欢迎直接开 [issue](https://github.com/yanqiyao1/coding/issues) 或者发邮件。我会改，并且会在文章末尾记一笔。
